# 07 知识库设计

知识库是本产品的主要护城河载体。**知识库的深度 = 产品的深度。**

## 1. 分层结构

| 层 | 内容 | 更新频率 | 维护方式 |
| --- | --- | --- | --- |
| L1 AI 能力目录 | 能力分类、成熟度、典型输入输出、可自动化系数基线 | 季度 | 内部维护 |
| L2 行业场景库 | 行业 × 业务域 × 流程节点 × 推荐能力 | 月度 | 内部 + 客户项目沉淀 |
| L3 案例库 | 真实项目案例:背景、做法、效果、成本 | 持续 | 项目交付沉淀 |
| L4 成本与价格库 | 模型调用价、人日单价、常见系统许可价 | 月度 | 内部维护 |
| L5 集成模式库 | API / RPA / 嵌入 / 独立部署 的适用条件与做法 | 季度 | 内部维护 |
| L6 合规库 | 行业监管要求、个人信息处理红线 | 季度 | 内部 + 外部专家 |
| L7 客户私有层 | 单个客户的画像、历史方案、实际效果 | 持续 | 自动写入 |

**隔离要求:** L1-L6 全局共享,L7 按租户严格隔离,任何检索都不得跨租户。

## 2. 条目 Schema

```json
{
  "id": "string",
  "type": "capability | scenario | case | pricing | integration | compliance",
  "industry": "string | null",
  "domain": "string | null",
  "node": "string | null",
  "capability_class": "string | null",
  "title": "string",
  "content": "string",
  "metadata": {},
  "source": "internal | project | external",
  "confidence": "high | medium | low",
  "updated_at": "timestamp"
}
```

## 3. 检索策略

- **混合检索:** 向量相似度 + 结构化过滤(行业、业务域、能力类别)。
- **过滤优先:** 先按行业与业务域做硬过滤,再做向量排序,避免跨行业噪声。
- **重排:** 用快模型对 Top 20 做相关性重排,取 Top 3-5 注入 Prompt。
- **必须回传 id:** 方案中的案例引用必须携带知识库条目 id,便于审计。

## 4. 冷启动

**目标:用最少投入让前 3 个行业可用。**

- 选定 3 个行业(建议:零售电商 / 连锁服务 / 制造)。
- 每个行业手工维护 20 个场景、5 个案例、1 套成本基准。
- 先做「结构化表格 + 全文检索」,不急于上向量库;条目超过 500 条再引入 Embedding。
- 冷启动内容来源:公开行业报告、政策文件、公开案例、自身或伙伴项目的真实数据。

**判断标准:** 冷启动完成 = 对任一目标行业客户,能给出 10 个以上有行业针对性的机会点。

## 5. 数据飞轮

**这是长期壁垒,必须从第一天开始记录。**

```
客户项目 → 采集画像 → 生成方案 → 落地实施 → 回填实际效果(outcome)
   ↑                                                    │
   └────────── 校准 ROI 基准与可自动化系数 ←──────────────┘
```

- 每个项目完成后,把「预期值 vs 实际值」写入 `outcome` 表。
- 定期用真实数据校准 L1 的可自动化系数与 L4 的成本基准。
- 校准后的基准再次用于新客户,形成精度优势。

**关键约束:** 早期即使没有产品,也要有 `outcome` 的采集表(可以先用表格工具),否则飞轮永远启动不了。

## 6. 质量守则

- 任何条目必须标注来源(`internal / project / external`)与置信度。
- 外部来源的内容不得直接作为 ROI 基准,只能作为参考区间。
- 涉及具体客户的数据必须脱敏后才能进入 L3。
- 条目要有有效期与复审时间,过期基准必须标记。
